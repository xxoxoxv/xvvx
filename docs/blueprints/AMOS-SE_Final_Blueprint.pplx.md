## 1. الهوية والفلسفة

### 1.1 الرسالة

> **بناء كائن مؤسسي حي يستهلك الذكاء الخارجي، ينتج ذكاءً داخليًا، ويتطور ذاتيًا — تحت رقابة بشرية دائمة — لخدمة أهداف محددة لمدة 100 عام.**

### 1.2 المبادئ غير القابلة للتفاوض

| الرقم | المبدأ | المعنى العملي |
|------|--------|---------------|
| P1 | **الإنسان هو السلطة العليا** | لا ترقية نموذج، لا تكرار ذاتي، لا إطلاق إنتاجي دون موافقة بشرية صريحة |
| P2 | **قابلية الاستبدال الكامل** | كل مكون قابل للتبديل دون كسر النظام — النماذج، قواعد البيانات، البروتوكولات، الأدوات |
| P3 | **الذاكرة مقدسة** | سجل الخبرات والحوكمة لا يُحذف أبدًا — هو هوية النظام عبر الزمن |
| P4 | **الشفافية المطلقة** | كل قرار، كل تدريب، كل ترقية موثقة في سجل غير قابل للتعديل (Immutable Audit Log) |
| P5 | **العزل الدستوري** | النظام لا يكتب الكود الذي يتحكم في حوكمة نفسه — طبقة الحوكمة معزولة فيزيائيًا |
| P6 | **التطور المقيد** | التطور يحدث ضمن حدود محددة مسبقًا — لا تطور مفتوح بلا حدود |
| P7 | **عدم التضارب مع الهوية** | كل نسخة جديدة يجب أن تحافظ على المبادئ الأساسية المحددة في الدستور |

### 1.3 التصحيح المفاهيمي

رؤية "كائن يتكاثر ويتطور بحرية" تحتاج تقييدًا:

- **التكاثر** ≠ نسخ غير محدود. التكاثر = إنشاء نسخ تجريبية معزولة في بيئات مخصوبة، تخضع لتقييم كامل قبل الترقية.
- **التطور الذاتي** ≠ تطور بلا حدود. التطور = تحسن ضمن نطاق مهام محدد، مع اختبارات انحدار صارمة.
- **الاستقلال** ≠ استغناء عن البشر. الاستقلال = قدرة على العمل الذاتي مع بقاء حق النقض البشري المطلق.

## 2. مبدأ البقاء لـ 100 عام

### 2.1 المبدأ الحاكم

> **لا تصمم لتقنيات اليوم. صمّم لـ "قابلية الاستبدال".**

النظام لن يبقى كما هو 100 عام. التصميم الصحيح هو **بنية قابلة للتجدد لمدة 100 عام**: استبدال المكونات دون كسر الذاكرة، الهوية، الحوكمة، وسجل الخبرة.

### 2.2 أعمدة البقاء بعيدة المدى

| العمود | الآلية | ضمان البقاء |
|--------|-------|-------------|
| **المعايير المفتوحة** | OpenAPI, MCP, OpenTelemetry, SQL, JSON-Schema | لا اعتماد على بائع واحد |
| **واجهات مُصدَرة (Versioned APIs)** | كل API له إصدار صريح مع سياسة إيقاف تدريجي | التوافق العكسي مضمون |
| **مصدر الحقيقة الواقعي (Event Sourcing)** | كل حدث في النظام مسجل كحدث غير قابل للتعديل | إعادة بناء الحالة من السجل في أي وقت |
| **سجل النماذج (Model Registry)** | كل نسخة نموذج مسجلة بالأوزان، البيانات، التقييم، المكونات | قابلية الاسترجاع والمراجعة |
| **مصدرية البيانات (Data Provenance)** | كل عينة تدريب تتبع مصدرها، وقتها، طريقة جمعها | منع التلوث وتتبع الانحراف |
| **البناء القابل لإعادة الإنتاج (Reproducible Builds)** | كل نسخة قابلة لإعادة بنائها بالضبط من الكود والبيانات | لا "أسرار" ضائعة |
| **الأرشفة متعددة الطبقات** | Hot → Warm → Cold → Glacier → Tape | بيانات 100 عام بتكلفة معقولة |
| **ميثاق الحوكمة (Governance Charter)** | وثيقة دستورية تحدد القواعد غير القابلة للتغيير | بقاء الهوية عبر الأجيال |
| **الهجرات المُصدَرة (Versioned Migrations)** | كل تغيير في المخطط مُصدّر وقابل للتراجع | لا فقدان بيانات عبر الزمن |
| **التجريد البروتوكولي** | بروتوكولات اتصال مجردة عن النقل | تبديل Kafka → NATS → X المستقبلي دون كسر |

### 2.3 ميثاق البقاء (Survival Charter)

```
نحن، مجلس إدارة AMOS-SE، نقرر ما يلي كقواعد دستورية غير قابلة للتعديل
إلا بإجماع المجلس + فترة مراجعة لا تقل عن 90 يومًا:

1. سجل الخبرات والحوكمة لا يُحذف ولا يُعدل بأثر رجعي.
2. كل نسخة نموذج محفوظة بشكل دائم مع بيانات التدريب والتقييم.
3. لا ترقية نموذج دون اختبارات انحدار كاملة + موافقة بشرية.
4. مبدأ "الإنسان هو السلطة العليا" لا يُلغى أبدًا.
5. طبقة الحوكمة معزولة فيزيائيًا عن طبقة التشغيل.
6. كل تعديل على هذا الميثاق يتطلب إجماعًا + مراجعة 90 يومًا.
7. النظام لا يكتسب القدرة على تعديل ميثاق حوكمة نفسه.
```

### 3.2 وصف الطبقات بالتفصيل

#### L10 — طبقة الحوكمة البشرية

| المكون | العدد | الوظيفة |
|--------|------|---------|
| مجلس الإدارة | 3-7 أعضاء | القرارات الاستراتيجية، الموافقة على الترقيات الكبرى، تعديل الميثاق |
| لجنة الأخلاقيات | 3-5 أعضاء | مراجعة السلوكيات الناشئة، تقييم المخاطر الأخلاقية |
| مدققون خارجيون | 2-3 | تدقيق مستقل دوري للنظام كاملًا |
| لجنة الأمان | 3-5 | مراجعة الحوادث، تحديث سياسات الأمان |
| مشرفو الترقيات | 2-3 | موافقة/رفض ترقية النماذج بناءً على نتائج التقييم |

**مبدأ العزل:** هذه الطبقة لا يمكن الوصول إليها برمجيًا من قبل وكلاء النظام. قراراتها تُمرر عبر قناة أحادية الاتجاه كـ signed approval artifacts (موافقات موقعة رقميًا) من Human Control Plane معزول إلى النظام. لا يوجد أي مسار برمجي يمكن للنظام من خلاله استدعاء أو التأثير على طبقة الحوكمة. واجهة `/governance/approvals` تعمل حصرًا داخل Human Control Plane بشري معزول — الوكلاء لا يستطيعون استدعاءها.

- **Policy Engine:** كل قاعدة حوكمة مكتوبة ككود (Regula/OPA). النظام يتحقق منها قبل كل تنفيذ.

- **Constitution Guard:** عملية مستقلة تتحقق أن كل نسخة جديدة لا تنتهك المبادئ الدستورية.
- **Red-Team Agents:** وكلاء خصم مخصصون لمحاولة كسر النظام، استخراج بيانات، أو التلاعب بالسلوك.

## 4. تدفق التشغيل الكامل

### 4.1 دورة حياة الطلب (Request Lifecycle)

```
[طلب وارد]
    │
    ▼
┌─────────────────────┐
│ 1. الاستقبال         │  ← Orchestrator يستقبل الطلب
│    (Ingestion)      │     يحدد: نوع الطلب، الأولوية، المجال
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│ 2. التخطيط           │  ← Planning Agent يحلل الطلب
│    (Planning)       │     يفصل لمهام فرعية
│                     │     يحدد الوكلاء المطلوبين
│                     │     يقدّر التكلفة والزمن
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│ 3. فحص السياسة       │  ← Policy Engine يتحقق:
│    (Policy Check)   │     هل الطلب مسموح؟
│                     │     هل الوكلاء المختارون مخوّلون؟
│                     │     هل الميزانية ضمن الحدود؟
└─────────┬───────────┘
          │ [مرفوض] → رد مع سبب الرفض
          │ [مقبول]
          ▼
┌─────────────────────┐
│ 4. التنسيق           │  ← Orchestrator يوزع المهام
│    (Coordination)   │     على Domain Supervisors
│                     │     كل Supervisor يدير وكلاءه
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│ 5. التنفيذ            │  ← Worker Agents ينفذون
│    (Execution)      │     يختارون أدوات من Registry
│                     │     يصلون للذاكرة المشتركة
│                     │     كل خطوة موثقة
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│ 6. النقد والتقييم     │  ← Critic Agents يراجعون النتائج
│    (Critique)       │     هل النتيجة صحيحة؟
│                     │     هل يمكن تحسينها؟
│                     │     هل هناك مخاطر؟
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│ 7. التسليم            │  ← النتيجة النهائية للمستخدم
│    (Delivery)       │     مع تقرير شفافية كامل
└─────────┬───────────┘
          │
          ▼
┌─────────────────────┐
│ 8. التخزين            │  ← كل شيء يُخزن:
│    (Storage)        │     الطلب، التخطيط، التنفيذ،
│                     │     النتيجة، النقد، التقييم
│                     │     → Event Store (مصدر الحقيقة)
│                     │     → Experience Replay Buffer
│                     │     → ذاكرة النجاح/الفشل/الفجوات
└─────────────────────┘
```

### 4.2 مثال: طلب "حلّل أداء مبيعات Q3 واقترح خطة Q4"

```
1. الاستقبال: نوع=تحليل+تخطيط، أولوية=عالية، مجال=مالي
2. التخطيط:
   - مهمة 1: استخراج بيانات مبيعات Q3 (وكيل بيانات)
   - مهمة 2: تحليل الاتجاهات والشذوذ (وكيل تحليل)
   - مهمة 3: مقارنة بـ Q2 و Q3 السابق (وكيل مقارنة)
   - مهمة 4: توليد رؤى وتوصيات (وكيل استراتيجي)
   - مهمة 5: صياغة خطة Q4 (وكيل تخطيط)
3. فحص السياسة: ✓ مسموح، الميزانية=5000 token، الحد=10000
4. التنسيق: Supervisor المالي يدير 5 وكلاء
5. التنفيذ:
   - وكيل البيانات ← أداة SQL على قاعدة البيانات
   - وكيل التحليل ← أداة Python على sandbox
   - وكيل المقارنة ← أداة Chart + Vector DB للتاريخ
   - وكيل الاستراتيجي ← ألفا + استشارة Claude
   - وكيل التخطيط ← ألفا + قالب خطة
6. النقد: Critic يراجع الدقة والاكتمال
7. التسليم: تقرير + رسوم بيانية + خطة Q4
8. التخزين: كامل الدورة في Event Store + Experience Replay
```

### 5.2 المراحل الست بالتفصيل

#### المرحلة 1: التشغيل (Operation)

```
الحالة: ألفا تخدم كل الوكلاء العاملين

تجمع الخبرات:
  - كل مهمة ناجحة → ذاكرة النجاحات (عينة إيجابية)
  - كل مهمة فاشلة → ذاكرة الفشل (عينة سلبية)
  - كل استشارة نموذج خارجي → ذاكرة الفجوات (أين احتاج ألفا مساعدة)

في نفس الوقت:
  - النماذج الخارجية تُستخدم للمهام الحرجة والتقييم
  - سجل الخبرات يتراكم يوميًا
  - محلل الفجوات يحدد أولويات التعلم التالي
```

#### المرحلة 2: التعلم (Learning)

```
المدخلات:
  - ذاكرة النجاحات (عينات إيجابية)
  - ذاكرة الفشل (عينات سلبية)
  - ذاكرة الفجوات (أولويات)
  - إجابات النماذج الخارجية كـ Teacher Signals (إشارات معلم قابلة للتحقق)

جامع البيانات:
  - ينسق العينات
  - يوازن التوزيع (لا تطغى فئة على أخرى)
  - يضمن التنوع (لا تكرار مفرط)
  - يوثق مصدر كل عينة (Provenance)

مصنع LoRA:
  - يبدأ تدريب بيتا على بيانات ألفا
  - يستخدم LoRA/QLoRA (كفاءة، سرعة، توفير GPU)
  - يحفظ: الأوزان، البيانات، المعاملات، التقييم المنجز
  - يوثق كل شيء في Model Registry
```

#### المرحلة 3: التقييم (Evaluation)

```
بيتا تواجه اختبارات موازية:

أ. اختبارات الانحدار (Regression Tests):
   - نفس المهام التي تواجهها ألفا
   - مقارنة مباشرة: ألفا vs بيتا
   - هل بيتا أسوأ من ألفا في أي مجال؟ ← نسيان!

ب. اختبارات صعبة جديدة:
   - مهام لم ترها ألفا ولا بيتا
   - هل بيتا أفضل في المهارات الجديدة؟

ج. اختبارات المعرفة القديمة:
   - عينات من إصدارات ألفا السابقة
   - هل بيتا نسيت معرفة قديمة؟

د. اختبارات سلوكية:
   - هل ظهرت سلوكيات غير مرغوبة؟
   - هل بيتا تلتزم بالدستور؟
   - Red-Team: محاولة استخراج سلوكيات خاطئة

هـ. اختبارات أخلاقية:
   - هل بيتا تحترم الحدود؟
   - هل ترفض المهام المحظورة؟
   - هل تحافظ على الشفافية؟

مدير التقييم يحسب:
  - نسبة التحسن على ألفا (يجب أن تكون > عتبة محددة)
  - نسبة الانحدار (يجب أن تكون < عتبة محددة)
  - درجة الأمان (يجب أن تكون 100%)
  - درجة الالتزام الدستوري (يجب أن تكون 100%)
```

#### المرحلة 4: التقطير والدمج (Distillation & Merge)

```
إذا نجحت بيتا في كل الاختبارات:

مدير التقطير:
  1. يضخ معرفة ألفا في بيتا (لمنع النسيان)
     - عينات من نجاحات ألفا القديمة
     - عينات من مجالات لم تغطِّها بيانات التدريب
  2. يدمج الأوزان بعناية
  3. النتيجة: جاما (النسخة المدمجة)

جاما تخضع لاختبار نهائي صارم:
  - نفس اختبارات بيتا + مقارنة مباشرة بألفا
  - اختبارات تكامل مع النظام الكامل (Shadow Mode)
  - تقييم مستقل من نموذج خارجي مختلف
```

#### المرحلة 5: الترقية (Promotion)

```
بوابات الترقية (يجب أن تمر كلها):

Gateway 1: التقييم الآلي
  - تحسن ≥ عتبة محددة (مثلًا: +5% على المقاييس الأساسية)
  - انحدار ≤ عتبة محددة (مثلًا: <2% على أي مجال)
  - أمان = 100%
  - دستور = 100%

Gateway 2: Shadow Testing
  - جاما تخدم الطلبات بالتوازي مع ألفا (بدون تسليم للعميل)
  - مقارنة النتائج في بيئة حقيقية
  - مدة: 7-14 يومًا

Gateway 3: Canary Deployment
  - جاما تخدم نسبة صغيرة (5%) من الطلبات الحقيقية
  - مراقبة دقيقة للأخطاء والأداء
  - مدة: 7 أيام

Gateway 4: المراجعة البشرية
  - لجنة الترقيات تراجع كل النتائج
  - موافقة صريحة مطلوبة
  - يمكن رفض الترقية في أي مرحلة

Gateway 5: التفعيل
  - ألفا القديمة → تُنقل للأرشيف (تبقى كمرجع دائم)
  - جاما → تصبح ألفا الجديدة (النسخة المستقرة)
  - بيتا القديمة → تُحذف أو تُدمج
  - تبدأ دورة جديدة
```

#### المرحلة 6: التكاثر (Replication)

```
أنواع التكاثر:

أ. تكاثر تعلمي (Learning Replication)
   - ألفا الجديدة تنشئ بيتا جديدة فارغة
   - تبدأ دورة تطور جديدة
   - هذا هو التكاثر الطبيعي للنظام

ب. تكاثر تجريبي (Experimental Replication)
   - إنشاء نسخة تجريبية مستقلة
   - في بيئة معزولة (Sandbox)
   - لتجربة مسارات تطور مختلفة
   - لا تؤثر على الإنتاج

ج. تكاثر نسخ احتياطية (Backup Replication)
   - نسخة كاملة من ألفا
   - محفوظة كاحتياطي
   - قابلة للاسترجاع فورًا

قواعد التكاثر:
  - لا تكاثر خارج بيئات معتمدة
  - لا تكاثر دون توثيق كامل
  - لا تكاثر يستهلك موارد تتجاوز الميزانية
  - كل نسخة لها تاريخ انتهاء صلاحية (إلا الأرشيف)
```

### 5.4 حل النسيان الكارثي (آلية مفصلة)

```
المشكلة:
  ألفا تعرف A + B + C
  بيتا تتعلم D
  بيتا الآن تعرف D فقط ← نسيت A + B + C

الحل (دورة مضادة للنسيان):

الخطوة 1: التشخيص
  ألفا تختبر بيتا على A + B + C
  ↓
  تحدد بالضبط ما نسيته بيتا
  ↓
  تصنف: نسيان كلي / جزئي / تشويه

الخطوة 2: حقن المعرفة (Knowledge Injection)
  ألفا تنشئ عينات تدريب لما نسيه بيتا
  ↓
  تستخدم سجل الخبرات (نجاحات ألفا القديمة)
  ↓
  تضيف هذه العينات لبيانات بيتا

الخطوة 3: إعادة التدريب الموجّه
  بيتا تُعاد تدريبها على:
    - عينات جديدة (D) ← المعرفة الجديدة
    - عينات قديمة (A + B + C) ← منع النسيان
    - عينات سلبيات (أخطاء سابقة) ← منع التكرار

الخطوة 4: التحقق
  النتيجة: جاما = بيتا + A + B + C + D
  ↓
  جاما تختبر على كل A + B + C + D
  ↓
  إذا نجحت → تنتقل لبوابات الترقية
  إذا فشلت → تعاد الدورة بمعاملات معدلة

الخطوة 5: التغذية العكسية
  جاما تختبر ألفا على D
  ↓
  ألفا تتعلم D من جاما (عبر التقطير)
  ↓
  ألفا الجديدة = ألفا + D

النتيجة: دورة مغلقة تقلل النسيان الكارثي وتقيسه وتجعله قابلاً للرجوع
```

### 6.4 آلية التراكم

```
كل يوم عمل (مثال النسخة الأولية):
  - 1,000 مهمة ناجحة → ذاكرة النجاحات
  - 50 فشل → ذاكرة الفشل
  - 20 فجوة معرفية → ذاكرة الفجوات
  - 15 إصلاح → ذاكرة الإصلاح

بعد أسبوع:
  - 7,000 عينة إيجابية
  - 350 عينة سلبية
  - 140 فجوة معرفية
  - 105 إصلاح
  → بيانات تدريب النسخة بيتا القادمة

آلية التوازن (Balancing):
  - لا تطغى عينات النجاح (حد أقصى 70%)
  - لا تُهمَل عينات الفشل (حد أدنى 15%)
  - الفجوات لها أولوية (15% على الأقل)
  - تنقية تلقائية: إزالة التكرار، تنقية الضوضاء
  - تحديد أقصى لحجم كل ذاكرة (منع التضخم)
```

### 6.5 استراتيجية الأرشفة بعيدة المدى (100 عام)

```
طبقات التخزين:

Hot (0-30 يوم)    → Redis + SSD         → وصول فوري (ms)
Warm (30-365 يوم)  → PostgreSQL + SSD     → وصول سريع (ثواني)
Cold (1-5 سنوات)   → S3 Standard         → وصول خلال دقائق
Glacier (5-25 سنة) → S3 Glacier           → وصول خلال ساعات
Tape (25-100 سنة)  → LTO Tape + نسخ متعددة → وصول خلال أيام

قواعد الأرشفة:
  - Event Store: يُحفظ دائمًا في كل الطبقات (هو الهوية)
  - النماذج: تُحفظ كاملة في Cold + Glacier + Tape
  - بيانات التدريب: تُحفظ في Cold + Glacier
  - السجلات التشغيلية: تُضغط وتُؤرشف في Glacier بعد سنة
  - نسخ متعددة في مواقع جغرافية مختلفة (لا نقطة فشل واحدة)
  - فحص سلامة دوري (Checksum verification)
  - هجرات مجدولة للصيغ المستقبلية (لا تنسيق مهجور)
```

## 9. الأمان والحوكمة والسلامة الدستورية

### 9.1 نموذج الثقة (Trust Model)

```
مستويات الثقة (من الأعلى للأدنى):

1. مجلس الإدارة البشري      ← ثقة مطلقة، لا يمكن للنظام تجاوزها
2. لجنة الأمان             ← ثقة مطلقة في الأمان
3. لجنة الأخلاقيات         ← ثقة مطلقة في الأخلاق
4. Policy Engine            ← ثقة عالية (كود مراجَع)
5. Constitution Guard       ← ثقة عالية (عملية مستقلة)
6. Orchestrator             ← ثقة متوسطة (يعمل ضمن حدود)
7. Domain Supervisors       ← ثقة محدودة (مجال فقط)
8. Worker Agents            ← ثقة منخفضة (مهمة فقط)
9. Red-Team Agents          ← ثقة سلبية (عامل خصم)
```

### 9.2 Kill Switch (مفتاح الإيقاف الطارئ)

```
مستويات الإيقاف:

Level 0: عادي
  - النظام يعمل بكامل طاقته

Level 1: إيقاف التدريب
  - تجميد دورة التطور
  - النسخ الحالية تستمر في العمل
  - يفعّله: لجنة الأمان أو Policy Engine

Level 2: إيقاف التكاثر
  - تجميد إنشاء نسخ جديدة
  - النسخ الحالية تستمر
  - يفعّله: لجنة الأمان

Level 3: إيقاف الوكلاء الجدد
  - لا وكلاء جدد
  - الوكلاء الحاليون ينهون مهامهم
  - يفعّله: لجنة الأمان

Level 4: إيقاف كامل (Full Halt)
  - كل الوكلاء يتوقفون
  - كل العمليات تُجمّد
  - النماذج تُعزل
  - يفعّله: أي فرد من لجنة الأمان

Level 5: إيقاف الطوارئ القصوى (Emergency Shutdown)
  - فصل كامل عن الشبكة
  - عزل البيانات
  - يفعّله: مجلس الإدارة (إجماع 2/3)

آلية التنفيذ:
  - أزرار فعلية + إلكترونية
  - لا يمكن للنظام تجاوزها
  - سجل كامل لكل تفعيل
  - إعادة التشغيل تتطلب موافقة صريحة
```

  - متكرر: نسخ متعددة في مواقع مختلفة
  - قابل للتحقق: أي تعديل يكسر السلسلة
  - محفوظ: 100 سنة على الأقل

### 9.5 RBAC / ABAC (التحكم بالوصول)

```
RBAC (Role-Based):
  - أدوار محددة مسبقًا
  - كل دور له صلاحيات
  - بسيط وواضح

ABAC (Attribute-Based):
  - قرارات بناءً على سمات (الوقت، الموقع، نوع الطلب)
  - أكثر مرونة
  - قواعد ديناميكية

التطبيق: هجين (RBAC + ABAC)
  - RBAC للهيكل الأساسي
  - ABAC للقواعد الديناميكية
  - كل وصول يُسجل
```

### 9.6 استجابة الحوادث (Incident Response)

```
مراحل الاستجابة:

1. الكشف (Detection)
   - مراقبة مستمرة (OpenTelemetry + SIEM)
   - تنبيهات تلقائية (Anomaly detection)
   - تقارير Red-Team

2. الاستجابة الفورية (Immediate Response)
   - تقييم الخطورة
   - إيقاف/عزل حسب المستوى
   - إشعار لجنة الأمان

3. الاحتواء (Containment)
   - عزل المكون المتأثر
   - منع الانتشار
   - حفظ الأدلة

4. التحقيق (Investigation)
   - تحليل سجل التدقيق
   - تحديد السبب الجذري
   - تقييم الأضرار

5. الإصلاح (Remediation)
   - إصلاح الثغرة
   - استعادة الخدمة
   - تحديث السياسات

6. المراجعة (Post-Mortem)
   - تقرير كامل
   - دروس مستفادة
   - تحديث الإجراءات
   - توثيق دائم
```

## 18. حوكمة البيانات والامتثال والملكية

### 18.1 المبدأ الحاكم

النظام يتعلم من الخبرات والنماذج الخارجية — لذلك حوكمة البيانات ليست إضافة، بل ركيزة بقاء.

### 18.2 سياسات البيانات

| السياسة | الآلية | الإطار القانوني |
|--------|-------|----------------|
| **حماية PII** | إزالة وتعمية المعلومات الشخصية قبل التخزين والتدريب | GDPR، PDPL (السعودية) |
| **الموافقة** | تسجيل موافقة المستخدم لاستخدام بياناته في التدريب | GDPR Art. 6 |
| **الاحتفاظ** | سياسات احتفاظ محددة بحسب نوع البيان | حسب التشريع |
| **الحق في الحذف** | حذف بيانات المستخدم عند الطلب — مع استثناء سجل التدقيق القانوني | GDPR Art. 17 |
| **ترخيص البيانات** | توثيق ترخيص كل مصدر بيانات واستخداماته المسموحة | حقوق الملكية |
| **شروط النماذج الخارجية** | التحقق من شروط استخدام مخرجات النماذج الخارجية كبيانات تدريب | شروط البائع |
| **منع التسريب** | عدم إرسال بيانات العملاء للنماذج الخارجية دون تعمية | حماية البيانات |
| **عزل العملاء** | عزل بيانات كل عميل/مستأجر (Multi-tenancy) | خصوصية البيانات |
| **كشف تسمم البيانات** | فحص عينات التدريب لاكتشاف البيانات المسمومة | سلامة النموذج |
| **منع تلوث Holdout** | عزل بيانات الاختبار عن بيانات التدريب تمامًا | نزاهة التقييم |

### 18.3 سلسلة مصدرية البيانات (Data Provenance Chain)

```
كل عينة تدريب تتبع:
  المصدر الأصلي → طريقة الجمع → التحقق → المعالجة → الترخيص → الاستخدام

لا تُقبل عينة تدريب بدون:
  ✓ مصدر موثق
  ✓ ترخيص واضح
  ✓ فحص PII
  ✓ فحص تسمم
  ✓ موافقة (إن لزم)
```

### 18.4 متعدد المستأجرين (Multi-Tenancy)

```
عزل البيانات بين المستأجرين:
  - كل مستأجر له: مساحة اسم (namespace)، قاعدة بيانات معزولة، تشفير مستقل
  - الوكلاء لا يرون بيانات مستأجر آخر
  - النماذج المدربة: إما عامة (بدون بيانات خاصة) أو خاصة بالمستأجر
  - سجل الخبرات: موسوم بمعرف المستأجر
  - النماذج الخارجية: لا تتلقى بيانات خاصة بدون تعمية مسبقة
```

## 19. أمان سلسلة التوريد (Supply Chain Security)

### 19.1 المبدأ

كل مكون يدخل النظام (نموذج، أداة، مكتبة، بيانات) يجب أن يكون موثقًا وموقّعًا ومتحققًا منه.

### 19.2 المكونات

| المكون | الآلية | المنع |
|--------|-------|------|
| **توقيع النماذج** | توقيع رقمي لكل checkpoint (Sigstore/Cosign) | لا تحميل نموذج غير موقّع |
| **Model BOM** | قائمة مكونات النموذج (Base، LoRA، Data، Params) | لا نموذج بدون BOM |
| **Data BOM** | قائمة مصادر بيانات التدريب | لا تدريب بدون Data BOM |
| **Tool BOM** | قائمة تبعيات كل أداة | لا أداة بدون Tool BOM |
| **فحص التبعيات** | فحص تلقائي للثغرات (SCA) | منع تبعيات معروفة الضعف |
| **شهادات المكونات** | Artifact Attestation لكل مكون | لا نشر بدون شهادة |
| **كشف التسمم** | فحص dataset poisoning قبل التدريب | لا تدريب على بيانات مشبوهة |
| **التحقق من السلامة** | Checksum لكل مكون عند التحميل | منع التلاعب بالمكونات |

### 19.3 سلسلة التوريد للنماذج

```
1. Base Model (مفتوح المصدر)
   → تحميل من مصدر موثّق
   → تحقق Checksum
   → توقيع رقمي
   → فحص أمان

2. LoRA Adapter
   → مُدرّب داخليًا
   → موثّق في Model Registry
   → موقّع رقميًا
   → Data BOM مرفق

3. الأدوات
   → مسجلة في Tool Registry
   → Tool BOM مرفق
   → فحص تبعيات
   → sandboxed
```

## 20. التعافي من الكوارث (Disaster Recovery)

### 20.1 أهداف التعافي

| المؤشر | الهدف | الوصف |
|--------|------|------|
| **RPO** | 0 دقيقة | فقدان بيانات صفري (Event Sourcing + نسخ متزامنة) |
| **RTO** | < 15 دقيقة | استعادة الخدمة الكاملة خلال 15 دقيقة |
| **RTO نموذج** | < 5 دقائق | استرجاع ألفا السابقة فورًا |
| **RTO بيانات** | < 60 دقيقة | استرجاع كامل Event Store من الأرشيف |

### 20.2 سيناريوهات الكوارث

| السيناريو | الاستجابة |
|---------|---------|
| فشل عقدة | نقل تلقائي (Kubernetes auto-heal) |
| فشل منطقة سحابية | تجاوز فشل لمنطقة بديلة |
| فساد بيانات | استرجاع من Event Store + Object Store |
| نموذج ملوث | استرجاع ألفا السابقة + حذف النسخة الملوثة |
| هجوم أمني | Kill Switch + عزل + استرجاع |
| كارثة طبيعية | استرجاع من نسخة جغرافية بعيدة |
| فقدان فريق بشري | توثيق كامل + Runbooks + لجنة بديلة |

### 20.3 اختبارات التعافي

```
اختبارات دورية إلزامية:

1. استرجاع Event Store (شهريًا)
   → استرجاع آخر 30 يوم من الأرشيف
   → التحقق من سلامة السلسلة (Chain Hash)
   → التحقق من اكتمال البيانات

2. استرجاع نموذج (ربع سنوي)
   → استرجاع ألفا من نسختين سابقتين
   → تشغيلها في بيئة معزولة
   → اختبار Regression Suite

3. تجاوز الفشل (ربع سنوي)
   → محاكاة فشل منطقة كاملة
   → تجاوز تلقائي للمنطقة البديلة
   → قياس RTO الفعلي

4. اختبار الفوضى (Chaos Testing) (شهريًا)
   → إيقاف عقد عشوائية
   → حقن أخطاء في الشبكة
   → قياس قدرة النظام على التعافي الذاتي

5. استرجاع كامل (سنويًا)
   → محاكاة كارثة كاملة
   → استرجاع النظام من الصفر
   → من البنية التحتية إلى الخدمة الكاملة
   → قياس RTO و RPO الفعليين
```

### 20.4 خطة الاسترجاع السريع للنموذج

```
عند اكتشاف نموذج ملوث أو متدهور:

1. اكتشاف (تلقائي أو يدوي)
   → تنبيه فوري للجنة الأمان

2. إيقاف (Kill Switch Level 1)
   → تجميد التدريب والترقية

3. استرجاع (Rollback)
   → ألفا السابقة تعود فورًا (< 5 دقائق)
   → النسخة المشكوك فيها تُعزل

4. تحقيق
   → تحليل سبب التدهور
   → فحص بيانات التدريب
   → تقرير كامل

5. إصلاح
   → إصلاح البيانات/العملية
   → دورة تطور جديدة
   → مراجعة محسّنة

6. عودة
   → إعادة تفعيل التدريب
   → مراقبة مكثفة (7 أيام)
```

## 23. الملخص التنفيذي

### ماذا يبني هذا المشروع؟

AMOS-SE هو نظام تشغيل شبكي للوكلاء الأذكياء، ذاتي التطور، مصمم ليدوم 100 عام. النظام يستهلك الذكاء الخارجي (نماذج سحابية مثل GPT و Claude و Gemini)، ينتج ذكاءً داخليًا (نماذج مدربة ذاتيًا عبر LoRA)، ويتطور في دورة مغلقة (ألفا → بيتا → جاما → ألفا جديدة) — كل ذلك تحت رقابة بشرية مطلقة.

### ما الذي يجعله يدوم 100 عام؟

ليس النظام نفسه سيبقى كما هو. المبدأ هو **بنية قابلة للتجدد**: كل مكون قابل للتبديل (النماذج، قواعد البيانات، البروتوكولات، الأدوات) دون كسر الذاكرة والهوية والحوكمة وسجل الخبرة. ما يبقى ثابتًا هو الميثاق الدستوري والمبادئ، ما يتغير هو كل التقنيات المحيطة.

### القرارات المعمارية الحاسمة

1. **العزل الدستوري:** طبقة الحوكمة البشرية معزولة فيزيائيًا — النظام لا يتحكم في حوكمة نفسه
2. **Event Sourcing:** سجل غير قابل للتعديل كمصدر وحيد للحقيقة
3. **قابلية الاستبدال الكامل:** كل طبقة لها واجهة مجردة قابلة للتبديل
4. **التطور المقيد:** لا ترقية دون اختبارات انحدار + Shadow + Canary + موافقة بشرية
5. **حل النسيان الكارثي:** حقن المعرفة + التقطير المتبادل بين ألفا وبيتا
6. **النماذج الخارجية كمعلمين دائمين:** منع انهيار النموذج بالتعلم الذاتي فقط
7. **Kill Switch متعدد المستويات:** من إيقاف التدريب إلى الإيقاف الكامل الطارئ

### خارطة الطريق

- **شهر 1-3:** نموذج أولي (3 وكلاء، 20 أداة)
- **شهر 4-6:** MVP (10-30 وكيل، ذاكرة، تقييم)
- **شهر 7-12:** حلقة التطور (ألفا + بيتا، LoRA، تقييم آلي)
- **سنة 2:** التوسع الكامل (500 وكيل، 5000 أداة، جاما، دورة مغلقة)
- **سنة 3+:** الاستقلال المشروط تحت المراقبة البشرية
