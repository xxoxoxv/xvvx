## 2. BLOCKER

### B1 — النواة السيادية كانت معزولة عن مسار التنفيذ (عُولج جزئيًا في هذه الجلسة)

القياس قبل العمل:

```
grep -rn 'from core\.\|import core' federal/ --include='*.py'   →  صفر نتيجة
```

`core/sovereignty/gateway.py` يصف نفسه بأنه «المسار الوحيد الذي يُنفَّذ من خلاله
أي فعل في الدولة»، ولم يكن أي ملف تحت `federal/` يستورده. كانت البوابة مُثبَتة
في العزلة (`tests/` و`tools/` تستوردانها) وغائبة عن التشغيل. أي أن كل ادّعاء
حَكْمٍ دستوري على أفعال الدولة كان — تشغيليًّا — غير مُنفَّذ.

**المعالجة في هذه الجلسة:** أُنشئت `services/executive_core` وفيها
`sovereignty_bridge.py` الذي يستورد `SovereignGateway` و`ActionRequest` فعليًّا،
ويسقط صريحًا (`SovereigntyUnavailableError`) إن تعذّر الاستيراد — بلا بديل صامت.
كل انتقال حالة للمهمة يُنفَّذ **داخل** `gateway.execute`، فلا كتابة خارج الإذن.

القياس بعد العمل: النتيجتان الوحيدتان لأمر `grep` أعلاه في
`executive_core/sovereignty_bridge.py` (السطران 150 و174).

**ما بقي منه:** `api_gateway` و`orchestrator` و`agent_runtime` تظلّ مساراتٍ
موازية لا تمرّ بالبوابة. توجيهها إلى النواة التنفيذية = البند R1 أدناه.

### B2 — تنفيذ الأدوات محاكاة كاملة

```
grep -c '_mock_' .../services/agent_runtime/sandbox.py   →  24
```

`ToolSandbox` كلّه دوالّ `_mock_sql_query` و`_mock_generation` وأمثالها. فأي
«مهمّة مكتملة» في الدولة اليوم مكتملة على صندوق أدوات محاكٍ. هذا ليس عيبًا في
النواة التنفيذية، لكنه يمنع وصف مسار المهمّة بأنه إنتاجي.

**المعالجة الجزئية:** كل نتيجة مهمّة تحمل الآن `execution_fidelity =
"SIMULATION"` صراحةً في القاعدة وفي الواجهة — الادّعاء مُعلَن لا مخفيّ.
استبدال الصندوق بأدوات حقيقية وحدة عمل قائمة بذاتها.

### B3 — `requirements.lock` غير قابل للتركيب في CI (عُولج جزئيًا)

كان الملف يحوي ست حزم من بيئة صندوق وكيل سابق، إحداها عجلة محلية:

```
pplx_sdk @ file:///tmp/asi-template-build/local-wheels/...whl
protobuf-perplexity-pb-llm-api-...  (أربع حزم)
pplx-python-sdks-llm-api==...
```

وبيئة CI تنفّذ `pip install -r requirements.lock` في مَهمّة `test`. مسار
`/tmp/asi-template-build/...` لا وجود له في عامل GitHub، فالخطوة تسقط قبل أي
اختبار. أي أن مَهمّة `test` في CI **لم تكن قادرة على النجاح** منذ دُفع هذا
الملف. حُذفت الأسطر الستّ (176 سطرًا باقية).

وبعد الحذف، بقي الملف غير قابل للتركيب لسبب ثانٍ **مقيس** بـ`pip install --dry-run`:

```
ERROR: Cannot install -r requirements.lock (line 45), (line 78) and protobuf==7.35.1
        because these package versions have conflicting dependencies.
  line 45: googleapis-common-protos==1.75.1
  line 78: modal==1.5.2
  line 111: protobuf==7.35.1
```

أي أن الملف ليس قفل مشروع بل `pip freeze` لبيئة صندوق كاملة: `modal` و
`googleapis-common-protos` ليستا من تبعيات المشروع في `pyproject.toml` أصلًا،
و`protobuf==7.35.1` يتعارض مع ما تطلبه `googleapis-common-protos`.

**لم يُعَد توليد القفل في هذه الجلسة، عن قصد.** إعادة توليده تغيّر تثبيتات
عشرات الحزم وتحتاج تحقّقًا كاملًا بحزم الاختبار الثلاث — وهي وحدة عمل مستقلّة، لا
ذيل لوحدة أخرى. المطلوب فيها: توليد القفل من `pyproject.toml` (`[project]` +
`[dev]`) **مع** الحزم التي تعتمدها الاختبارات فعلًا ولم تُعلَن في `pyproject`
(`matplotlib` مثالًا مقيسًا: اختبار أداة الرسم يسقط بدونها)، ثم إثبات
`pip install -r requirements.lock` في بيئة نظيفة.

## 3. REQUIRED NEXT PHASE

### R1 — توجيه `api_gateway` و`orchestrator` إلى النواة التنفيذية

اليوم: `api_gateway` يستقبل الطلب، و`orchestrator` يبني خطة وينشر حدثًا ثم
يُنسى الأمر (لا مستهلك ينقل المهمّة إلى تنفيذ). النواة التنفيذية تملك دورة
الحياة الكاملة، فالمطلوب أن يصبح مسار الطلب الخارجي:
`api_gateway → executive-core (8008) → agent_runtime`، وأن يبقى `orchestrator`
مُخطِّطًا فقط (النواة تستدعي `build_plan` منه فعلًا الآن).

### R2 — وصل `tool_registry` و`model_gateway` بمسار التنفيذ

الوكيل ينفّذ خطوة بأداة نصّية، ولا أحد يسأل سجلّ الأدوات عن وجود الأداة ولا عن
شروط استخدامها، ولا يمرّ نداء نموذج ببوّابة النماذج. الخدمتان مبنيتان ومُختبَرتان
ومعزولتان — وصلهما شرطٌ لأي تنفيذ حقيقي (وهو مقدّمة لحلّ B2).

### R3 — سجل الوكلاء الحقيقي

جدول `agents` لم يكن يقرؤه أحد قبل `dispatcher.py`، وتوليد السكان في
`governance/expansion.py` يعتمد `FULL_POPULATION_CATEGORIES` ثابتة (مرصودة في
مصفوفة الحقيقة كـ HARDCODED_TRUTH). المطلوب: دورة حياة وكيل حقيقية (تسجيل،
ترقية، عزل، سحب) على القاعدة، تُغذّي الموزّع.

### R4 — جعل CI مُلاحَظًا

بوابة `verify_cross_system_suites.py` لم تكن موصولة بـ`ci.yml` (قيس:
`grep -c verify_cross_system_suites .github/workflows/ci.yml → 0`). أُضيفت في هذه
الجلسة مَهمّة `cross-system-suites` مع خدمة PostgreSQL 17. لكن **نتيجة CI نفسها
غير مُلاحَظة من هذه البيئة**: المستودع خاصّ و`api.github.com` خارج نطاق الاعتماد
المتاح. الحال الصادق: **UNOBSERVED**، لا PASS ولا FAIL.
